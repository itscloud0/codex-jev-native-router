# Versioned Shadow policy comparison — 2026-09-23

The `completion_v1` policy adapts useful ideas from `0xNatoshi/jev-codex-router`: account for retries, corrections, context rebuilding, model capability, and cache-switch cost. It does not copy their per-call architecture, hardcoded model identifiers, or mandatory Astra rule. It uses our discovered model catalog and configured allowlist. Auto remains on `baseline`; Shadow can run `completion_v1`.

The read-only replay used 48 stratified historical first-user requests from the local Codex index. Each request was sanitized and clipped before transmission. Jev saw only the bounded task dossier. Output records contain pseudonymous IDs and decision metadata, not task text, source, tool output, keys or full conversations. Both policies ran on the same cases with Luna/Terra/Sol allowed and Astra excluded.

Models agreed on 9/48 cases, efforts on 37/48, and the exact model/effort pair on 8/48. Each policy returned 47 direct Jev decisions and one decision-cache reuse. The candidate strongly favors Sol, which may improve hard-task completion or may waste Pro allowance on easy tasks. Historical manual model choice and first-turn text do not identify the correct executor. This replay **does not measure quality, total completion usage, or savings**; it is a disagreement and regression signal.

Small low-overhead additions: the Desktop adapter now passes only the previous turn's integer cached-input percentage when native Codex reports it; the candidate treats this as a switching-cost hint, never a capability ceiling. Route telemetry records the policy version, and `effortlane report` groups proposals by policy. Neither feature stores prompts. The candidate stays in Shadow until outcome-labeled task comparisons support promotion.

## Work-shape policy — 2026-09-25

`completion_v3` replaces one large model/effort Choice with two independent questions in a single Jev call: work shape (`mechanical`, `routine`, `substantive`, `unknown`) and reasoning depth. Code maps shape to the catalog/allowlist, preserves risk and large-context floors, and sends `unknown` to Sol. No numeric confidence gate is enabled without outcome calibration.

Seven synthetic, privacy-safe probes checked obvious boundaries in English and Russian. V3 chose Luna/low for a variable rename, Terra/medium for a bounded parser, Sol/high for integration debugging and security architecture, Sol/medium for an evidence-poor "Continue the task", Luna/low for a README edit, and Sol/high for a Russian integration bug. V2 chose Luna/low for that evidence-poor continuation and Sol/medium for the debugging probe. The remaining role choices matched. These examples justified the initial v3 rollout but were **not** a SWE quality benchmark or a Pro savings measurement. Shadow retains v2 for comparison. Review real corrections, retries, cache behavior, and task outcomes before claiming an improvement.

## Long-context switch guard — 2026-09-25

The installed v3 policy had an absolute 48k-token Sol floor and a second lease rule that allowed downgrades only in short sessions. In one six-hour sample, 22 of 24 Desktop Auto routes were above the threshold and all 24 executed Sol. This was a policy failure for the goal of evaluating cheaper models, despite healthy Jev and native execution.

V4 leaves Luna and Terra eligible at any measured context size. It keeps the deterministic risk floor and `unknown`→Sol behavior. When a previous stronger model has a context above the configurable threshold or at least 80% measured cache reads, v4 waits for three distinct valid Jev recommendations for the same cheaper role before switching. An invalid answer, Jev outage, or Sol recommendation resets the streak. Upgrades remain immediate. The streak is metadata only; no prompt or source is persisted. This is a heuristic to limit cache thrashing, not a calibrated confidence gate or proof of Pro allowance savings.

Unit tests cover the long-context switch, reset, hot-cache guard, manual choice, and timeout fallback. A live Jev probe on three simple turns proposed Luna each time and selected it on the third; a native `codex exec --jev-auto` smoke chose Luna/low and completed correctly. A vague CLI request chose Sol/medium. These are function tests, not a quality or savings benchmark. Existing Desktop app-server processes must restart before using v4.

After v4 promotion, the original Shadow v2 setting was not comparable with Auto v4. New installs and the reference configuration now run Shadow v4: Sol remains the executor and the proposal follows the same policy as Auto. Earlier v2 receipts remain in historical reports under their own policy version.

## Observed usage audit — 2026-09-30

The local telemetry spans only about 50 hours, not a full subscription week. In a 72-hour query it contains 5,202 Auto-attributed model calls, but only 151 calls link to 155 pre-turn route decisions; 5,051 calls are unlinked and cannot prove what Jev chose for them. The old CLI gateway accounts for most of these. Of the 156 Auto route events seen in the raw 72-hour window, 129 selected GPT-6 Sol, 27 Luna, and none Terra. Work shape was `unknown` 70 times. Only two events recorded a model switch. This is evidence that the router is conservative, not evidence of an optimal policy.

On the 5,048 calls with a published model rate and recorded token counts, the observed mix is 4,220.6946 Codex credit-equivalent units versus 4,239.9610 for hypothetical all-GPT-6-Sol at the **same token counts**: about 19.27 units, 0.45%, before Jev. Legacy records did not mark whether cached-input details were actually present, so this is a sensitivity estimate. The 12-hour recent window is better linked: 26 Auto-attributed calls, all linked to pre-turn routing, 18 priced, observed mix 19.2118 versus all-GPT-6-Sol 22.3875 (14.2% same-token difference). These samples do not measure correction cost, task quality, actual Pro allowance debits, or TypeSafe billing. The currently published GPT-6.1-Sol cached-input credit rate is half GPT-6-Sol's; all-6.1-Sol is a lower-cost comparison for new work, but not a historically available baseline for these older calls.

The 72-hour Auto-attributed token records contain about 636.5M input tokens, 622.3M marked cached (97.8%), and 1.64M output tokens. This argues against a general cache-collapse explanation for the user's fast weekly usage depletion. The large volume and long-lived sessions are more plausible contributors, but these records do not prove causation. Public Codex credits are a proxy rather than Pro allowance accounting; TypeSafe publishes a [$0.042/M input-token rate with free output](https://typesafe.ai/blog/introducing-system-one-models-and-jev), so 80,088 metered Jev input tokens imply roughly $0.00336 at the published rate; actual account billing and promotional credits are unknown. `effortlane savings --hours 12` and `effortlane savings --hours 168` now expose the link gap and cache-detail provenance. New records explicitly mark when native cached-input detail is absent so they cannot be priced as if all input were uncached.

The routing policy was not changed from v4 in this audit. A chat-wide permanent model floor would be speculative: the measured cached-input ratio is already high and switching is rare. The actionable next measurement is a comparable task cohort with corrections, retries, elapsed time, and all model calls linked to pre-turn routes, then compare Auto to fixed GPT-6.1 Sol at equivalent quality. Jev receives no full thread or source to improve its decisions; it already receives bounded task text plus context size and recent cache/switch state. More raw history would increase privacy risk and Jev latency without established benefit.

## Chat-level model affinity and per-turn effort — 2026-09-30

OpenAI's [prompt-caching guide](https://developers.openai.com/api/docs/guides/prompt-caching) says that cache reuse depends on the unchanged rendered prefix. The cache stores KV tensors; switching models should not be assumed to preserve the same cached states. Changing top-level `reasoning.effort` can also change hidden instructions and the prefix. GPT-6 has a cache-preserving `configuration_update` mechanism for effort changes, but the installed CLI and Desktop-bundled Codex both report `reasoning_effort_override` as an under-development feature that is disabled. Upstream Codex issues [#44751](https://github.com/openai/codex/issues/44751) and [#47843](https://github.com/openai/codex/issues/47843) report compatibility and behavioral bugs, so enabling it globally now is not justified.

A privacy-safe 72-hour analysis of current v4 Auto receipts found 63 routed sessions, 16 with multiple turns. Across adjacent decisions in those sessions there were 70 unchanged model/effort pairs, 22 effort-only changes, and only two model changes. Linked successor usage showed about 97.0% weighted cache reads for unchanged pairs and 97.6% for effort-only changes. These observational data do not show a general cache collapse from effort changes on this Mac; they also do not prove effort changes are free, because task size, age, and cache provenance differ. The two model-switch successors had 0% and about 80% cached input, respectively. The second was a return to a previously used model. Two examples are insufficient to estimate a general model-switch penalty.

The user's proposed policy is a useful hypothesis, not yet a proven replacement: choose model and effort at chat start, upgrade the model immediately for a material capability need, preserve model affinity for later small turns, and change effort more freely. V4 already implements immediate upgrades and long-context/hot-cache downgrade hysteresis, but not a calibrated switch-cost test or effort hysteresis. It uses the current sanitized turn plus previous work shape, model, context length, and cache hint; it does not have a reliable structured signal for task change or recent correction outcome. A permanent no-downgrade rule would be too rigid for a new task in the same chat or an expired cache.

Next candidate should be measured in Shadow before Auto: compare v4 against a chat-affinity policy with a bounded task-change and failure/correction signal, model downgrade only when expected completion benefit exceeds likely cache/reconstruction cost, and effort hysteresis only when current cache evidence warrants it. Keep capability upgrades and manual choices immediate. Compare linked input/cached/output tokens, elapsed time, correction/retry rate, and task completion against fixed GPT-6.1 Sol. Do not claim Pro allowance savings from same-token credit prices, and do not activate cache-preserving effort updates until supported in the installed Codex build and smoke-tested on the actual models.

## Metadata hypothesis and release safeguards — 2026-09-30

On September 28 (Asia/Tbilisi), Auto telemetry contains 5,070 model-call records from 34 sessions: 5,063 GPT-6 Sol and 7 Luna. The 4,924 calls with token counts show 623.9M input, 610.6M cached (97.87%), 13.3M uncached, and 1.57M output tokens. These are model calls, not user turns or Pro allowance units. The 6.1 Sol metadata warning happened in our first September 30 smoke after the CLI upgrade; only three 6.1 Sol calls exist in this telemetry, all from our smokes. Consequently the observed 6.1 metadata bug cannot explain the September 28 volume. We cannot rule out a separate historical metadata problem for 6 Sol without historical Codex warnings or model-catalog snapshots, but the high measured cache ratio does not support a broad cache-collapse theory.

Codex [warns when model metadata falls back](https://github.com/openai/codex/issues/12100), and its [model schema](https://github.com/openai/codex/blob/main/codex-rs/protocol/src/openai_models.rs) includes context, compaction, effort, and tool capabilities. Best practice for this integration is to fetch the authenticated catalog with the same native binary that will execute the turn, keep Desktop and standalone CLI catalogs separate, and pass the native CLI catalog to routed `exec`, including the Jev-error fallback. A Codex [schema-mismatch report](https://github.com/openai/codex/issues/38934) reinforces the need to avoid copying a newer CLI catalog into an older Desktop binary. Keep catalog validation in `doctor` and after updates; never assume a new model slug alone is sufficient. This safeguard is implemented and tested, but a successful `doctor` is a local/static check, not proof that every future Codex release will route correctly.

For usage, OpenAI's [prompt-caching guide](https://developers.openai.com/api/docs/guides/prompt-caching) says the model and earlier rendered prefix determine reuse; switching models or changing effort can alter cache behavior. The local Auto data recorded only two model switches, so rapid Sol/Luna thrashing was not observed. Avoid a permanent model floor or a fixed per-turn downgrade rule without outcome evidence. Shadow on fixed Sol at user-selected effort is the safer reference while collecting linked task completion, retries, latency, and token data. Cached-token counts are useful diagnostics, not a direct conversion to the ChatGPT Pro weekly allowance.

## Post-restart feature checks and Chrome crash — 2026-09-30

After the restart, the running Desktop thread's native rollout records GPT-6.1 Sol/medium. Router selection and pre-turn telemetry agree: `jev-shadow`, executor GPT-6.1 Sol/medium. Installed bootstrap, RPC adapter, and manager files match the repository. Local doctor passes. A built-in ImageGen request generated a red-square image, and `automation_update` in read-only `view` mode rendered an existing automation. This verifies image generation and automation viewing through the active Desktop wrapper; it does not test automation creation, scheduled execution, or every host feature.

A fresh plain CLI `codex exec --ephemeral --skip-git-repo-check --json` returned the expected marker with exit 0. Its linked route and usage events show Shadow executing GPT-6.1 Sol/medium while Jev proposed GPT-6 Luna/low. Usage was 22,254 input, zero cached input, and 9 output tokens. This is a short functionality smoke, not a coding quality or savings benchmark. The global default is now Shadow/medium; existing chats with explicit selections can differ.

The supplied Chrome crash is a startup SIGABRT in `TransformProcessType → _RegisterApplication → abort`. The system log for the exact crashed PID records denied Mach lookups to `com.apple.coreservices.launchservicesd` and `com.apple.CoreServices.coreservicesd` immediately before the abort. This supports a macOS sandbox/GUI-registration failure, consistent with upstream [Codex issue #30043](https://github.com/openai/codex/issues/30043). ChatGPT being the responsible process establishes launch ancestry, not that the router caused the failure. The wrapper does not launch Chrome or change the native executor's sandbox policy. The exact originating browser tool has not been identified, and a wrapper-on/off reproduction has not been performed for this Chrome incident.

A separate headless `about:blank` probe outside the command sandbox, using an isolated temporary Chrome profile, timed out after 25 seconds. No remaining test-profile Chrome process was found during cleanup. Browser functionality therefore remains unverified. Prefer the supported host browser tools; an external browser launch that needs LaunchServices access should use a narrowly approved unsandboxed command, not globally disable Codex sandboxing or repeatedly retry the failing sandboxed launch. The crash report's 50.4 GB VM total is virtual address space, not evidence of 50.4 GB resident RAM or swap.

### Chrome launcher identified and local mitigation

Subsequent bounded rollout inspection identified the exact originating command: another Desktop chat launched system Chrome through Playwright in a sandboxed shell. Its output records `<launched> pid=9548` followed by SIGABRT, matching the attached crash report and system denials. The same chat immediately reran its Playwright command with `sandbox_permissions=require_escalated` and completed with exit 0. A fresh isolated Playwright `about:blank` probe outside the command sandbox also completed successfully with Chrome 154.0.8037.58; a second probe explicitly enabled `chromiumSandbox: true` and exited 0. This narrows the incident to the shell browser launch boundary rather than the Jev routing decision or ImageGen endpoint.

The local global `~/.codex/AGENTS.md` now instructs agents to prefer host browser tools, request narrowly scoped elevation before an external Chrome/Chromium launch, retain isolated profiles and browser cleanup, and avoid retrying the failing sandboxed path. The prior instructions were backed up and the update was atomic. This is an instruction-level mitigation, not a deterministic launch interceptor or a patch to Codex's sandbox. Agents ignoring the instructions, existing scripts, and other launchers can still encounter the upstream failure. Router execution, authentication, model policy, and OS sandbox settings were not changed.
